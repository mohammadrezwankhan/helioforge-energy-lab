# From useful release to a 5,000-star ambition

Stars are an external community outcome. There is no honest implementation that guarantees 5,000 stars, an award, adoption or product-market fit. Do not buy engagement, spam communities, fabricate customers or place a false achievement badge in the UI.

## Positioning

A narrow, testable promise is stronger than “all energy systems”: **explore hybrid architectures, learn from explainable scenarios, and inspect the exact numerical evidence**. Lead with the hybrid lab and the first hospital-outage experiment. Show the 19/17 numerical/study distinction prominently. Explain why conceptual 3D and explicit model boundaries help people learn.

## Milestones and evidence gates

| Stage | Goal | Evidence before the next stage |
|---|---|---|
| Release candidate | A stranger runs the demo without help | Five independent clean installations; OS/browser notes; no blocking setup issue. |
| Credible technical release | Calculations can be challenged outside the implementation | Three independently reproduced benchmarks; peer-reviewed units, policy and terminal-state treatment; licensed fixtures. |
| Useful learning tool | Lessons teach more than labels | Five educator/practitioner reviews; correct misconception handling; observed completion and confusion notes, collected with consent. |
| Contribution-ready | Outside contributors can add value without a rewrite | Ten well-scoped issues; at least three external accepted contributions; reviewed catalogue/lesson templates; documented release process. |
| Public launch | The demonstration is easy to understand and share | Working static preview, a 60–90 second walkthrough, two reproducible case-study articles and clear limitations on the landing page. |
| Sustainable growth toward 5,000 stars | Repeat usefulness rather than one launch spike | Track real stars, clones, installations, issue quality, returning contributors and benchmark reproductions after publication. No success promise or invented timetable. |

The numbers above are proposed acceptance targets, not achieved metrics. Prefer retention and independently validated usefulness over star count alone.

## Launch assets included

Actual desktop/mobile screenshots, a standalone preview, README walkthrough, capability matrix, example inputs, original lesson catalogue, issue templates, contribution guide, CI definition, manual preview-only GitHub Pages workflow and a final audit. Repository publication, Pages activation, external outreach and paid provider tests still require owner action/authorization; none happened in this build.

## Release checklist

Run clean CI on all declared Python versions. Inspect package contents and generated data. Review licences and scan full Git history for secrets. Remove private project context and database files before publication. Configure a private security-reporting channel. Run direct-browser tests and assistive-technology checks. Review the optional AI terms and cost controls in your own API project. Record exact versions, artifacts and observed limits in each release.

## Outreach that earns attention

Publish a reproducible outage comparison and invite technical critique. Share in relevant research, education and energy communities according to their posting rules, with limitations visible. Offer newcomer-sized benchmark and accessibility issues. Respond constructively to invalid results. Maintain a short, evidence-backed changelog. Do not claim 5,000-star readiness on visuals alone.
